# VCC telemetry development verification — 2026-09-28

## Scope

- Firmware: `cmd.get_power()` on V3 and V4. V3 measures voltage only, as confirmed by the maintainer; current/power are unsupported, not zero. V4 uses its existing voltage and current ADC conversions and calculates power.
- Host: `Device.get_power()`, CLI `power-read --port <command-port> --json`, MCP `get_power()` in `codex/0.2.3-dev`.
- User skill: entrypoint route, tool index and `references/power-telemetry.md`.
- Query sends only `cmd.get_power()`, has no power-control or SWD initialization fallback, rejects active stream sessions, and preserves legitimate zero readings. CLI uses a probe-only connection; ordinary MCP connect retains its existing target initialization behavior.

## Wire contract

One line prefixed `MKLINK_POWER ` followed by a JSON object:

```json
{"schema":1,"voltage_mv":3300,"current_ua":12345,"power_uw":40739,"current_supported":true,"sample_age_ms":10}
```

The values above are fixtures, not measured hardware data. Host returns `voltage_mv`, `current_ma`, `power_mw`, `current_supported`, `sample_age_ms`.
The integer firmware calculation is `(voltage_mv * current_ua + 500) / 1000` using a 64-bit intermediate.
Unavailable ADC values are JSON null. V3 always reports `current_supported=false`, null current and null power. The firmware publishes a coherent software snapshot from the existing filtered ADC readings; this does not imply simultaneous analog sampling. Warm-up requires ten successful samples. ADC failure invalidates its measurement, and power requires both voltage and current. The host rejects stale snapshots older than 1000 ms, malformed frames and unsupported firmware; it does not invent zero values or automatically change VCC.

## Initial build-stage hardware limitation

No physical MKLink command port was available during this verification. No new firmware was flashed, and ADC electrical accuracy has not been certified. ## Subsequent V3 hardware verification

Later on 2026-09-28 the maintainer connected a V3 probe and an STM32H743 board. The probe reported V3.5.1 and already supported the new command. No probe update, target program modification or target reflash was needed.

- Raw firmware command: 10 successful reads, 3247–3248 mV.
- CLI JSON/text: six independent connections succeeded; JSON stdout contained only the result.
- Real MCP subprocess over stdio JSON-RPC with the physical serial port: 20 successful reads, 3246–3248 mV, mean 3247.45 mV. Snapshot age 0–9 ms.
- Every reading reported `current_supported=false`, null current and null power.
- MCP disconnect/reconnect followed by the first `get_power` succeeded, at 3248 mV. CLI subsequently reacquired the port, verifying serial release.
- H743 DHCSR before/after the MCP sequence was 0x02010000 / 0x00010000. S_HALT was clear at both observations; the second read did not report another reset since the first read cleared the reset status.
- No supply-switch, voltage-setting, target reset, halt or target write command was issued. Ordinary MCP connect performed its existing debug initialization. The original project configuration was preserved; a separate test session directory was used.

Raw responses, CLI output, MCP results and server stderr are retained locally in the provided target project's `.mklink/power-telemetry-20260928/`, not uploaded. The test exited with a passing result and all command sessions closed.

This establishes V3 interface functionality and session interoperability. There was no external meter comparison, power switching or physical power-cycle test. V4 current/power and the customer's H563 AP issue remain unverified by this H743 run.
