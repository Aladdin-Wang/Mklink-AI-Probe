# VCC telemetry development verification — 2026-09-28

## Scope

- Firmware: `cmd.get_power()` on V3 and V4. V3 measures voltage only, as confirmed by the maintainer; current/power are unsupported, not zero. V4 uses its existing voltage and current ADC conversions and calculates power.
- Host: `Device.get_power()`, CLI `power-read --port <command-port> --json`, MCP `get_power()` in `codex/0.2.3-dev`.
- User skill: entrypoint route, tool index and `references/power-telemetry.md`.
- Query sends only `cmd.get_power()`, has no power-control or SWD initialization fallback, rejects active stream sessions, and preserves legitimate zero readings. CLI uses a probe-only connection; ordinary MCP connect retains its existing target initialization behavior.

## Wire contract

One line prefixed `MKLINK_POWER ` followed by a JSON object:

```json
{"schema":1,"voltage_mv":3300,"current_ua":12345,"power_uw":40739,"current_supported":true,"sample_age_ms":10}
```

The values above are fixtures, not measured hardware data. Host returns `voltage_mv`, `current_ma`, `power_mw`, `current_supported`, `sample_age_ms`.
The integer firmware calculation is `(voltage_mv * current_ua + 500) / 1000` using a 64-bit intermediate.
Unavailable ADC values are JSON null. V3 always reports `current_supported=false`, null current and null power. The firmware publishes a coherent software snapshot from the existing filtered ADC readings; this does not imply simultaneous analog sampling. Warm-up requires ten successful samples. ADC failure invalidates its measurement, and power requires both voltage and current. The host rejects stale snapshots older than 1000 ms, malformed frames and unsupported firmware; it does not invent zero values or automatically change VCC.
