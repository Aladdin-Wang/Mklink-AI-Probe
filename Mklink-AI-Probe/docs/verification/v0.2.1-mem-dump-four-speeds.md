# HPM5301 mem_dump: four speed profiles

Development branch: `codex/v0.2.1-development`. Verification date: 2026-09-13.

## Behavior

| Profile | Requested debug clock | SuperWatch label |
| --- | ---: | --- |
| `low` | 4 MHz | Low |
| `medium` | 10 MHz | Medium (default) |
| `high` | 20 MHz | High |
| `ultra` | 30 MHz | Ultra |

Existing saved `high` selections retain their 20 MHz meaning. A new HPM session
without a saved selection defaults to `medium`. SDK, CLI, MCP and Web use the
same profile application code. The Web endpoint persists a selection only after
the device accepts it; a subsequent failed selection does not overwrite it.

20/30 MHz require the supported HPM JTAG interface and the probe's exact
JTAG-kernel acknowledgement. HPM6E80 testing subsequently established that
the JTAG ID is shared: it does not identify HPM5301 or qualify another board.
The API now reports profile confirmation without claiming exact target identity.
See [the separate HPM6E80 record](v0.2.1-hpm6e80-mem-dump.md).
A generic clock echo, a zero profile or a different profile is insufficient.
Unsupported HPM firmware restores a conservative 1 MHz clock and reports an
error. ARM and other targets do not acquire 20/30 MHz qualification from this
change. Changing profiles through the SDK/MCP requires an idle stream; the Web
application stops dashboard streams before applying its selection.

CLI supports `debug-speed ultra`, `dump-benchmark --speed ultra` and
`dump-memory --speed ultra`. MCP supports `set_debug_speed(profile="ultra")`
and the `speed_profile` argument on `measure_dump_memory` / `dump_memory`.
Omitting that argument preserves the connected session's selection.

## Validation method

Both clock settings use the same HPM5301 board, wiring, running target program
and bounded-memory capture harness. Firmware versions are distinguished below.
No target firmware
changes, target memory writes, ordinary mem_read/mem_write benchmark or RTT
benchmark are part of this qualification.

The original candidate underwent 30-minute fixed 4-byte Flash streams and
5-minute contiguous 64-byte streams at both speeds. The 30 MHz suite also passed
2 minutes each of 4 KiB blocks and changing RAM, plus ten reconnections exercising
all four profiles with four noncontiguous addresses. The original 20 MHz suite
failed during its 4 KiB case and was stopped; its remaining cases were not run.

The repaired firmware has a separate qualification suite: 4 KiB for 600 seconds
at 20 MHz and 300 seconds at 30 MHz; fixed 4 B and contiguous 64 B for 30 seconds
each at each speed; changing RAM for 120/30 seconds at 20/30 MHz; and ten
reconnections exercising all four speeds with four noncontiguous addresses.
This is 48 cases. Known contents are compared against the target image for every
received complete sample; dynamic RAM is checked for value changes.

Each case checks layout, block order, CRC, drop/error flags and strictly
increasing probe timestamps. Start-up command text is recorded separately from
stream corruption. DMI and USB diagnostics are collected after stopping the
stream. A mismatch, integrity failure or prolonged absence of samples stops the
suite rather than automatically retrying it.

Rates exclude the first 200 ms and include batch gaps. Each 4 KiB logical sample
consists of two 2048-byte B1 frames; the endurance harness counts the sample and
timestamps it at completion of the second frame. Earlier short-test reports and
the public benchmark API use the first block timestamp after verifying complete
coverage. Those timing conventions must not be silently mixed.

## Verification status

The repaired firmware passed all 48 cases: 20,052,146 complete logical samples
and 291,041,390 DMI scans. CRC errors, frame loss, firmware error/drop flags,
DMI reserved/failed/busy results and USB errors/full/blocked time were zero.
Seven SBA busy conflicts occurred in the 20 MHz 4 KiB case; all seven recovered
and all contents matched. Other cases recorded no new SBA faults. Ten reconnect
cycles successfully exercised all four profiles. The suite restored 10 MHz and
released the probe.

The 30 MHz block run ended with one uncompleted trailing half-block, excluded
from the complete-sample count. Four-byte and 64-byte regression cases had no
intervals over 1 ms. A complete 4 KiB block naturally takes several milliseconds;
its interval must not be confused with a stalled single-variable sampler.
30 MHz improves current fixed-value sampling by 13.9% and 4 KiB throughput by
17.0% relative to 20 MHz. This repaired-image test did not demonstrate sustained
sampling above 100 kSa/s; earlier 109 kSa/s short results are a different run.

For comparison, the original firmware's 30-minute fixed-value runs measured
94.165 kSa/s at 20 MHz (169,091,712 samples) and 99.675 kSa/s at 30 MHz
(178,976,184 samples). Both passed their own content/integrity checks, but the
old 20 MHz suite subsequently failed in the 4 KiB case. The differing durations
and images do not establish a controlled throughput regression or improvement.

Passive LA5032 captures at 500 MSa/s measured actual TCK of 19.909 MHz and
29.809 MHz inside complete 41-bit Shift-DR scans. All 4,870 / 5,725 complete
DMI responses in these respective captures had status zero. These short logic
captures supplement the longer data checks; they do not replace them.

Software checks: 143 affected Python tests, 3 SuperWatch component tests,
production TypeScript/Vite build, and 72 packaging/update/boundary tests passed.
Real CLI and MCP stdio passed 24 interface operations: all four profile
acknowledgements, period benchmarks, known-value samples, omission preserving
the current speed, and restoration of the saved default. Chrome applied all
four choices and displayed changing single-variable curves at 20/30 MHz
(approximately 86.4/98.5 kSa/s in API snapshots). CRC, backend errors and drops
were zero. The two GUI acquisitions accumulated 92 startup-text bytes, 46 each;
these were not reported as lost binary frames.

Applying 30 MHz while sampling stopped the old backend stream before changing
the clock; the viewer's status poll then enabled Start again. The subsequent
30 MHz curve worked. Final state was stopped, saved 10 MHz, disconnected.
Screenshots were captured through the Chrome GUI and retained as local evidence.
An obsolete saved Pack identifier initially prevented the source GUI from
connecting; its backup was retained and the project was rebound to the existing
exact HPM5301 local SVD before successful acceptance. No fallback chip was used.

The committed runtime snapshot `245314f` was subsequently installed through the
standard Skill archive installer. All 2,460 installed archive files matched
their hashes, maintainer content was absent, and the previous installation was
backed up. A fresh installed CLI exposed all four choices; a fresh installed
Web process applied 30 MHz and displayed a live Chrome curve at approximately
98.1 kSa/s with zero CRC/read errors and drops. It was stopped, restored to
10 MHz and disconnected. Existing already-running AI/MCP processes need a
restart to load the new runtime; no official release or installer was published.

## Firmware fault found during qualification

Original candidate UF2 SHA-256:
`751049018b8cf90150d55f857b367a846af99b8e11961c73192c4c8e0e65f717`.
Its 20 MHz 4 KiB stream failed at 24.85 seconds with a region-read error despite
zero CRC, DMI and USB errors. A diagnostic build reproduced the error at
95.06 seconds and latched SBCS `0x20558407`: a sticky SBA busy conflict, with
no SBA bus error and no bus transaction still pending. Reading SBDATA with
read-on-data enabled starts another bus read, and overlapping a busy SBA access
can set this conflict flag.
[RISC-V Debug Module specification](https://docs.riscv.org/reference/debug/debug_module.html).

Repaired UF2 SHA-256:
`2927de9be7c0350cdc467addcbb2db8b961e5456c3de6817d09222cb016a11c5`.
It retains the normal fast path and permits one bounded, fully checked replay
only for this confirmed conflict in a whitelisted HPM5301 XIP chunk of at most
512 B that has not yet been published. The recovery checks readiness before
every word and disables automatic reads before the final word. RAM/MMIO,
real bus errors, uncertain DMI failures and a second failure are not replayed.
Fault and recovery counts remain observable; recovered conflicts must not be
reported as zero conflicts. The old failed suite is retained as failed, and
its earlier long runs are not attributed to the repaired firmware.

Five SBA model configurations and 6,976 instruction-model scans of the actual
assembled JTAG kernel passed. The new image builds successfully; diagnostics
add 24 bytes of DLM state without enlarging the sampling buffers.

## Scope

This qualifies the tested HPM5301 setup, not every probe, cable, voltage,
temperature or target family. HPM6E80 requires a separate connected-board test.
Sampling is not hard real-time or an atomic snapshot of multiple variables;
finite USB buffering cannot guarantee loss-free acquisition under arbitrary
host stalls. Published release channels and the desktop installer are unchanged.
