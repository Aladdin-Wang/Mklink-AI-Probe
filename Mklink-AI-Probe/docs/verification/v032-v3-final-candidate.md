## 未收敛的实际失败

`15-flash-matrix` 的在线任务已经完成 erase/program/verify/reset，RTT8、Watch4
自动恢复检查通过。但随后在采集并行状态下进行完整 Flash 回读，出现
`Serial worker write failed`，矩阵中止，不能将整项标为通过。

失败后 USB 及两路串口仍正常枚举，worker 进程仍在；明确重新连接在 0.52 秒内
恢复，芯片 ID 再次正常。未重插、修改供电、重刷固件或盲目重放烧录。
这些现象尚不足以判断故障来自主机还是固件。固件会话正在只读协查。

上位机检查发现 `SerialException` 继承 `OSError`，导致 worker 返回的具体错误也被
统一包装成写入失败。当前源码保留原异常，普通管道错误保留其原因文本；6 项相关
测试通过。此修改还未进入上述冻结包，不能用旧包通过代替新代码验收。

显式重新设置 medium（10 MHz）后，两轮并行完整回读分别 411.591/410.858 秒，
均与原 512 KiB 逐字一致；Watch 仍运行且读错/丢弃为 0，RTT8 正常。
随后脱机部署/触发、校验失败、主动停止、共享烧录恢复通过；停止采集后再回读
512 KiB（45.548 秒），仍与备份相同，冻结后台已正常退出。
这些结果保留首发失败，不能自动消除此门槛。V3 Keil/OpenOCD 和最终新包仍待测。

固件会话发现独立的 V3/V4 时钟恢复遗漏：在线下载使用 1 MHz，随后新建 MUX 的
目标 attach 路径未恢复应用保存的时钟。显式重设 10 MHz 的补测不是原失败的等价条件。
固件修复后候选 V3.6.3 / V4.6.7 已交付、哈希独立核对，尚未刷入；此修复不能直接
归因为串口失败的根因。源码正按下载后不手动改时钟的路径复现。

异常透传源码 `88ea563c` 的完整 Python 回归：4635 通过、2 跳过，741.97 秒；
60 条现有 websockets 弃用警告。对应构建包装器日志保留于本地 `.build/reports`。
相关 CI 已通过。源码复现首次因故意缩窄 PATH 后无法加载本机 libusb，在线入口返回
404，尚未执行烧录；恢复已安装 libusb 所在目录后重新启动，此环境失败独立保留。

源码 `88ea563c` 随后完成原路径复测：在线下载使用 1 MHz，恢复 RTT8/Watch4 后不手动
重设时钟，完整 512 KiB 回读与备份一致，流程 428.025 秒。未复现串口错误，不能据一次
成功判定该偶发问题已修复。停止两个采集后约 82 秒，下一步时钟对照返回会话过期 409；
期间没有主动关闭客户端，因此尚无时钟速率对照结论。

## SDK 心跳续租修复

源码确认单次临时心跳 HTTP 错误会永久结束续租，原 5 秒请求超时也耗尽整个 5 秒租约。
新增测试在原代码上 8 失败、4 通过；修复后相关生命周期、共享设备、退出回归 109 通过。
心跳现在使用 2 秒超时，仅对临时 IPC/500/502/503/504 失败重试，连续三次失败结束；
明确的 401/403/409 等拒绝立即结束。始终使用原端点和原会话，不创建新会话、不重放硬件
操作；过期会话不可复活。该缺陷可以解释一类空闲后失效，但首发实机未保留心跳错误，
不能声称已证明它就是本次 82 秒后过期或串口写错的原因。

完整 Python 正在按新增心跳修复重新运行；新 Windows 冻结包及 V3.6.3 实测待完成。
