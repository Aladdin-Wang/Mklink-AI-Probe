# 0.3.2 SuperWatch 瞬态读取失败恢复

## 用户现象与边界

30 MHz、1 kHz 下收到 `SuperWatch target read failed (status 5)` 即停止采集。
用户报告下载器屏幕 MCU 图标断开/灰色，Keil 下载时短暂恢复，再次 Watch 可以采样却仍灰。
用户明确要求不新增灰色/未知中间状态：瞬态读错保留连接，持续无有效读取才显示断开。

主机会话继续维护 `codex/0.3.2-fixes`，下载器固件交给既有固件会话。
该会话仍在操作 V3 硬件；本次未访问串口、SWD、VCC 或烧录目标。

## 根因与修复

- 主机 `mux_watch.py` 原来把所有非 0/9 状态直接作为致命异常，包括状态 5。
  异常从 `DumpMemoryStreamSession` 传到 SuperWatch 采集线程，finally 发送 Watch stop。
  同一次 drain 中已解码的有效样本也会因异常失去返回机会。
- 对照固件源码，状态 5 是一次目标读失败，快批次或逐区域路径仍保留 Watch 订阅。
  它不是 USB 断开或 DAP 更换目标的专用事件，不能单次触发永久停止。
- 格式合法的状态 5 现在清除不完整样本、累计读取错误与缺口，然后接收后续样本。
  不补零、不插值、不复位、不重发写入/启动命令，不自动降速。
- 首次失败启动单调时钟窗口；只有完整有效样本才清除窗口，零散区域不足以恢复。
  连续失败或失败后无数据达到 `max(3 秒, 3 × 配置周期 + 0.5 秒)` 才报告持续读失败并停止。
  纯空闲、正常批次间隔或 DAP 等待不凭空视为读失败；传输错误仍立即终止。
- 状态 7（目标被 DAP 改变）、其他未知错误及格式/传输损坏仍明确报错。
  既有 `read_errors` 状态字段汇总固件读取失败，`stream_integrity.firmware_read_errors`
  保留计数；不声称错误事件数量等于丢失的采样点数。
- 主机此路径不主动关闭共享 USB 连接。屏幕 MCU 图标由固件连接状态机负责；
  已向固件会话同步 V3/V4 二态语义和采样成功恢复要求，固件修改/实机结果另行交接。

## 验证

本地 383 项通过：MUX、dump-memory session、RTT/SuperWatch streaming、实时写入、独立服务健康。
新增回归包含普通/压缩批次瞬态恢复、有效数据前后时间戳保留、不重放命令、
持续失败、一次错误后静默、完整多区域样本恢复、慢采样、DAP 失效、真实传输失败。
采集管理器测试确认状态 5 后继续发布有效样本、保持 running/connection，用户停止时才发 stop。

尚未实测本次源码对真实 V3/V4、Keil、30 MHz 的表现，也尚未重新制作 Windows 安装包。
已交付的 `d8b08304` Mac/Linux 候选不包含本次修复，不得将其称为新错误恢复版本。
固件释放设备后，应测试：偶发错误继续采集、持续断目标后的停止、目标恢复与图标、
Keil 下载后再次 Watch、共享 RTT 不被连带终止，以及失败/停止后资源释放。
