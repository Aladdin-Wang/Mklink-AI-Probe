# FreeRTOS SystemView framing correction

The HPM documentation run produced valid raw RTT data but the host decoder
reported about one dropped byte per tick. Replaying the saved 105400-byte
capture reproduced 5007 dropped bytes and 15036 events.

Two host-parser defects caused this result:

- Length-prefixed RTOS API IDs 32–511 were rejected. The target's SEGGER
  FreeRTOS integration emits ID 36 for `vTaskDelayUntil` (5000 events here)
  and ID 35 for `vTaskDelay` (5 events here). Preserve these as opaque raw
  events, including their timestamp deltas. Existing payload bounds and the
  declaration check for dynamic modules starting at ID 512 remain in place.
- SEGGER `RecordSystime` emits two U32 varints, low then high, for SYSTIME_US.
  The parser consumed only the low part and mistook the high part for the delta.
  Decode both parts, combine them in the existing `systime` value, then read
  the timestamp delta. This removes the remaining two-byte alignment loss.

Protocol evidence came from the exact local target integration:
`SEGGER_SYSVIEW_FreeRTOS.h` (`apiID_OFFSET`, delay hooks) and
`SEGGER_SYSVIEW.c` (`SEGGER_SYSVIEW_RecordSystime`). No probe or target firmware
change is necessary for these corrections.

Verification:

- 143 SystemView Python tests passed, including new synthetic API and 64-bit
  systime cases split across 1/2/7/4096-byte input chunks.
- The original hardware capture, SHA256
  `ddd7d025d25188866242a90cdfc27d63c67de2ca86f7ca2daa70a0494f21ed88`,
  decodes to 20036 events, zero dropped bytes/packets, and no buffered remainder.
- Replays with chunk sizes 1, 7, 64, 512 and 4096 produce identical event lists
  and timestamps to whole-buffer decoding.
- Hardware capture replay is not a new live CLI/MCP/Web acquisition. The
  documentation task will perform installation and live retesting separately.

Raw API records remain opaque; this patch does not add RTOS API name decoding
or certify every SystemView event emitted by every target integration.
