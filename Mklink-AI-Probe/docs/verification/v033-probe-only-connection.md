## 最终行为

USB 身份匹配且命令口握手成功即可连接下载器，不要求目标板或有效 IDCODE。
已有目标识别是容错的信息查询，不作为下载器连接的成功条件；目标读写和采样仍须
正常目标通信。恢复已保存时钟失败时，健康的 USB 会话保持连接并报告警告；
USB/命令口本身失效仍报错并释放连接，不伪造成功。

低/中/高/超高档均接受下载器精确返回 `set clock <Hz>`，无需目标相关的
`SWD/JTAG profile` 行。可选 profile 确认仍单独通过 `profile_confirmed` 表达，
不能与下载器接受设置或测量物理频率混同。没有确认接口时返回 `interface=unknown`。
命令自身回显、计数器、错误码或明确不匹配的 profile 不冒作成功。

GUI、SDK、MCP、CLI 复用同一实现。GUI 保存频率会同步命名档位；MCP/CLI
保存档位会同步频率。非标准低速清除过时档位；仅有旧 debug_speed 配置的连接也会恢复。
页面改为“下载器设置速率”，撤销“先连接目标板”的提示，提供无需目标板的重试说明。

## 复现与真机验证

用户明确确认本机 V3 已断开目标板，仅保留 USB。版本 V3.6.4，全过程 IDCODE=0。
使用临时项目，未改用户工程设置，未烧录、写变量、复位目标或改变供电。

修复前在本机复现：10 MHz 成功，20/30 MHz 均因缺少 profile 确认返回错误并回退
1 MHz。这复现了客户日志中的时钟问题；最新截图中笼统的 Internal Server Error
没有异常栈，本机未重现该特定报错，不能声称它的全部原因均已确定。

修复后使用源码共享后台与最终生产 Web：

| 入口 | 结果 |
|---|---|
| 连接时恢复 20 MHz | connected=true、IDCODE=0、clock_hz=20000000、无警告 |
| SDK | 4/10/20/30 MHz 全部成功；profile_confirmed=false，如实表示无额外档位确认 |
| 实际 MCP stdio 子进程 | connect、ultra=30 MHz、disconnect 通过 |
| 实际 CLI 子进程 | debug-speed high --save 成功，20 MHz 状态一致 |
| 断开重连 | SDK 先释放，再经 GUI 使用的 REST 断开重连，恢复已保存的 20 MHz |
| 实际浏览器 | 在 IDCODE=0、已连接状态下从 20 改为 30 MHz，显示下载器设置速率 30 MHz 和已自动保存 |

仅一个共享后台占有命令口，各入口没有启用直连回退。浏览器结束后关闭自有会话和代理，
检查端口释放。照片、设备身份、临时路径及原始输出仅保留在忽略的本地构建目录。
