# 0.3.0 后台诊断日志收敛

## 问题与实现

原后台由启动进程把 stdout/stderr 永久追加到 runtime.log；既不轮转，也不限制单次
输出。多个 GUI/AI 使用同一后台后，该文件会跨会话长期增长。

后台取得既有 owner 锁后，在导入服务器前安装公共诊断流，复用标准库
RotatingFileHandler。现有 print、服务器 logging 和异常堆栈进入同一 runtime.log，
按 2MiB 轮转，保留 3 个备份；每次写入最多 1024 字符。标准库在编码前判断轮转，
UTF-8/替换编码可能超出阈值至多一个小块，不能解释为严格恰好 2MiB。
旧超大文件只读取并保留至多 2MiB 尾部，避免整文件读入或保留无界旧格式备份。

每台下载器仍在各自后台目录写日志。只有持有 owner 锁的进程能修改运行日志，
没有新增 GUI 日志管理器、守护进程、消息队列或硬件重试。诊断写入/轮转失败时，
标准 logging 的生产模式避免向同一 stderr 递归报错或中断硬件调用；此时日志可能丢失。

真机首轮连接发现 flash 模块导入时重配全局 stdout/stderr，导致诊断流没有
reconfigure 方法而连接失败。删除库模块这段全局副作用，控制台 UTF-8/replace
策略统一到既有 CLI 入口，不向日志适配器添加无效兼容方法。

## 第二轮：原生标准输出统一轮转

第一轮仍把原生系统句柄输出留在 startup.log，未消除该文件在运行期持续增长的可能。
第二轮在同一诊断上下文中接管 CRT stdout/stderr 和 Windows 标准句柄；通过进程内
匿名管道与单个读取线程送入原有分块流和 RotatingFileHandler。没有第二套轮转策略、
磁盘暂存或额外服务进程。初始化完成后，原生标准输出和继承这些句柄的子进程输出
进入相同的 4 个日志卷，startup.log 仅保留初始化前诊断，每次启动覆盖。

读取侧使用标准增量 UTF-8/换行解码，处理跨块字符和 Windows CRLF，避免重复回车。
管道本身提供有限缓冲；没有无界内存队列。退出恢复 CRT 描述符、可继承性和 Win32
标准句柄，排空已有数据；若子进程仍持有管道，不无限等 EOF，持续输出最多再排空
约一秒后关闭读取端。日志关闭后仍写入旧继承管道的子进程可能收到断管，不代表日志无损。

新增真实进程测试覆盖 CRT、Win32、子进程输出、超过容量的连续原生输出、句柄恢复、
缺失 stdout/stderr 的无控制台情形、空闲子进程持有写端时退出不挂起。退出后没有遗留
日志线程。日志测试 **10 项通过**；共享 CI 同集 **139 项通过**。

真实后台、Edge、SDK、MCP 再次进行混合 Python/CRT/Win32 输出压力验证：仅 4 个
有界运行日志文件，最新原生结束标记可见，startup.log 大小保持 0；GUI/MCP RTT 与
SDK 附着保持。Boot 不变、VTOR 为 0x08005000、tick 推进，没有设备写操作。后台
正常退出、锁释放，浏览器无 pageerror/HTTP 5xx，截图检查通过。第二只仅枚举。

这是 Windows 源码进程验证，不能代替 24/72 小时长稳、磁盘耗尽实测或安装包验收。
PyInstaller/NSIS、非 Windows 原生句柄行为和安装升级尚未验收。
