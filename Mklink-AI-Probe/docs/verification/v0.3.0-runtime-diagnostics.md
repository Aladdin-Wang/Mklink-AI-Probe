# 0.3.0 后台 Python 诊断日志收敛

## 问题与实现

原后台由启动进程把 stdout/stderr 永久追加到 runtime.log；既不轮转，也不限制单次
输出。多个 GUI/AI 使用同一后台后，该文件会跨会话长期增长。

后台取得既有 owner 锁后，在导入服务器前安装公共诊断流，复用标准库
RotatingFileHandler。现有 print、服务器 logging 和异常堆栈进入同一 runtime.log，
按 2MiB 轮转，保留 3 个备份；每次写入最多 1024 字符。标准库在编码前判断轮转，
UTF-8/替换编码可能超出阈值至多一个小块，不能解释为严格恰好 2MiB。
旧超大文件只读取并保留至多 2MiB 尾部，避免整文件读入或保留无界旧格式备份。

每台下载器仍在各自后台目录写日志。只有持有 owner 锁的进程能修改运行日志，
没有新增 GUI 日志管理器、守护进程、消息队列或硬件重试。诊断写入/轮转失败时，
标准 logging 的生产模式避免向同一 stderr 递归报错或中断硬件调用；此时日志可能丢失。

真机首轮连接发现 flash 模块导入时重配全局 stdout/stderr，导致诊断流没有
reconfigure 方法而连接失败。删除库模块这段全局副作用，控制台 UTF-8/replace
策略统一到既有 CLI 入口，不向日志适配器添加无效兼容方法。

## 验证

- 共享后台契约与 CLI/烧录模块相关回归 **194 项通过**，其中共享 CI 子集 **134 项**。
  新增测试已进入共享 CI：输出/错误/异常、超大 Unicode 输出、旧日志裁剪、并发写入、
  目录隔离、轮转失败不递归，以及 flash 导入不修改宿主输出流。
- 真实后台进程、Edge、MCP stdio、SDK 与主 V4/F103：GUI RTT 运行时，私有测试线程
  向后台 stdout/stderr/logging 写入超过 10MiB。结束时只有 4 个运行日志文件，各卷
  在约 2MiB 范围内，最新结束标记仍在；MCP 持续读取历史，GUI RTT 和 SDK 保持。
- Boot 前 20KiB 不变，VTOR 仍为 0x08005000，tick 推进；没有复位、烧录、擦除、
  改时钟或 VCC。第二只下载器仅重新枚举。后台最终正常退出，端口锁释放。
- 无 pageerror/HTTP 5xx，截图已检查。GUI 未修改，沿用前轮生产资源。
  首轮导入失败不是验收通过；修复后完整重跑。私有日志、标识和截图留在 .build。

## 尚未覆盖的边界

启动诊断与原生库直接写继承系统句柄的输出改为 startup.log，每次启动覆盖。
它没有运行期容量硬上限；本轮约束的是 Python 诊断，不表示全部原生输出已经有界。
该边界仍需收敛，不能把此轮短时压力验证当作 24/72 小时长稳或磁盘耗尽实测。
PyInstaller/NSIS、跨平台原生句柄行为和安装升级尚未验收。
