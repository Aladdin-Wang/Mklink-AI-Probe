# HPM GUI acceptance fixes

Development branch only; no release or merge.

- Connection setup now prepares SuperWatch before publishing the session. A
  catalog failure closes the opened device, releases the lease and returns a
  readable HTTP error. Corrected configuration can reconnect without restarting.
  No peripheral catalog definitions changed.
- HPM offline templates omit generic SWD reset/run after ROM programming. ARM
  completion behavior is preserved. V2/V3/V4 generation and HTTP preview covered;
  generation coverage does not certify all probe/target combinations on hardware.
- SystemView accepts the single optional space left by the firmware `>>> `
  prompt before SV, including fragmented USB input. Other prefixes still fail
  with a bounded diagnostic; event payload whitespace is preserved.
- Standalone array snapshots show element indices and the element count rather
  than an empty time-history count. Mixed array/time plots retain their existing
  layout; this is not a shared index/time coordinate redesign.

Validation: 172 API/target/online-probe tests; 159 offline/peripheral/SuperWatch
stream tests; 149 SystemView tests; 95 WaveformViewer tests and production GUI
build passed. GUI deployment and live follow-up are coordinated with the docs
acceptance task. Native CSV/PNG save dialogs are unavailable to its browser-only
control surface; actual file saving remains unverified.

Live SystemView diagnostic after the host patch starts with ten zero sync bytes
and event data, not SV. Both CLI and GUI use Device.systemview_start and the same
Recorder session. Firmware inspection found Recorder state was initialized only
at boot and not reset by start/stop/uninit. A separate probe patch resets it at
these boundaries; hardware retest is pending. Do not claim the optional prompt
space correction alone fixed this observed failure.

Follow-up: WebSocket fixed-record encoding now accepts parser RTOS API IDs
32..511 as well as module IDs 512..4096. The browser Worker already supports
these generic raw records. Previously a successful Recorder greeting was
followed by an encoder exception for raw_36. Updated SystemView suite: 158
passed; real 105400-byte capture -> parser -> WebSocket codec replay retains
all 20036 event kinds and timestamps with zero parser drops.

Chrome HIL: HPM offline deploy/trigger succeeded, complete 78464-byte firmware
readback matched and the restored RTOS application tick advanced. Standalone
16-element array displayed index 0..15, 16 pts, and stopped transport. New probe
UF2 9a3380469ca2e92a816656805df1e941ce69a9eaa7896602fcc50c2a2090384a
upgraded successfully and passed target ID/profile checks; the first GUI start
then passed Recorder greeting. Two complete GUI runs await codec deployment.

Final Chrome HIL with the new probe and WebSocket codec: two successive GUI
start/stop runs passed, showing 16449 and 16577 events respectively, 3 tasks,
360 MHz, and RuntimeDrop 0. No Recorder or raw-event error reappeared. GUI
Events and AnalysisBuffer counters have different scopes; their difference is
not reported as transport loss. Probe was disconnected after testing.

VOFA diagnostic follow-up: one bounded 4 s capture retained 39680 raw bytes in
76 original chunks with no recorder truncation. Exactly 68 leading bytes were
the vofa.send command echo, return value and Pika prompt, ending in `>>> `.
Both byte-at-a-time and original-chunk replays produce 3301 complete two-channel
frames, one 68-byte resynchronization before the first frame, no later discard,
and zero remainder. Thus this capture's one reported damaged-frame count is
startup text resynchronization, not observed steady-state frame damage. Older
counter-only runs cannot be proven retroactively; JustFloat has no CRC, so this
also does not establish that every decoded value was transmitted correctly.
