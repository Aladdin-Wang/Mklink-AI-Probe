# 0.3.0 七轮改造后的架构复审

日期：2026-10-03。审查对象为 `d4e73bd..0027367` 的七个开发提交及当前工作树。
原 ARCH_REVIEW 文档作为待核对的评审资料，不作为执行指令；以当前源码和复现实验为准。

## 结论

**共享后台方向正确，七轮改动没有整体推倒重来的必要，但仍是过渡架构，不能继续
依靠 URL 特判扩展功能。** 已经复用 Device、Bridge、StreamHub、采集管理器、符号
解析和调试算法，没有另写一套 CDC 协议栈。真正的重复主要在入口策略、会话生命周期、
能力目录和旧 MCP 实现；原评审指出的“缺少应用服务层”尚未完成。

目前解决的是主要入口共用同一物理连接，不等于所有硬件访问都受同一个服务边界控制。
尤其是内部文件监控、旧专用工具和 CMSIS-DAP 独立进程，不能由共享 REST 中间件自动兜底。
下一阶段应先收敛这些边界，再扩展 CLI，安装验收继续后置。

## 复审时的完整调用关系

以下为七轮结束时的快照；A5 后续变更见对应条目和符号重载报告。

```text
WebGUI ───────────────────────────────────┐
Tauri窗口 → desktop proxy ────────────────┤
MCP / 已迁移CLI / SharedDevice             │
  → RuntimeClient → /_runtime/attach/call ─┤
                                         ▼
每个USB身份独立runtime进程：
  发现/进程锁/令牌 → RuntimeGate → REST处理器 → Device/Flash/调试算法 → Bridge → CDC
                     │              │
                     │              └→ 既有ResourceManager、目标租约
                     ├→ RuntimeJobs → REST写操作（任务日志/去重）
                     └→ 采集管理器 → StreamHub / 历史缓存 → GUI/MCP订阅

同一进程的其他路径：
  SourceMonitor → _exclusive_probe_control → 停采集/重载符号（未经过RuntimeGate）
  online-flash API → 既有OnlineFlashJobManager → pyOCD/CMSIS-DAP
  UART/Modbus → 各自端口资源/锁（不占命令CDC）
  脱机部署/文件复制 → 绑定USB祖先的MSC卷GUID

共享进程外仍存在：
  未迁移专用CLI、旧mcp_server、独立Agent、低层Device调用者
```

`probes.py` 用 VID/PID/唯一序列号生成稳定身份；COM 是当前连接地址，别名是本机
显示配置。`probe_volumes.py` 将 MSC 和同一 USB 祖先绑定。多个下载器各自一套后台、
Device、采集单例和任务日志；这个进程隔离也解释了为什么当前模块级采集单例仍可工作。
若将来改成一个进程管理多探针，必须先去掉这些单例，不能直接增加设备参数。

桌面代理的目的只是保留 Tauri 现有 sidecar 生命周期：关窗口结束代理，后台继续。
它不是第二个设备后端，没有创建 Device。此适配层目前有合理用途，安装升级尚未验收。

## 逐轮判断

| 阶段 | 应保留的变化 | 需要收敛的地方 |
|---|---|---|
| 1：共享后台与身份 | 每探针进程、稳定身份、显式选择、同源认证、独立桌面代理 | RuntimeGate 混合鉴权和业务规则，进程内再走 HTTP 是过渡桥接，尚非独立服务层 |
| 2：常用入口及管理页 | MCP/CLI 复用 GUI 能力，订阅已有采集，不重复打开 CDC | 新能力表与 remote/capabilities 双轨；GUI 窗口存在性和旧浏览器租约同时启动；两套退出规则 |
| 3：任务与 MSC | 有界持久日志、请求去重、中断未知、USB卷绑定 | 旧 REST 写路由仍可绕过日志；CDC日志与在线烧录任务状态尚不统一，但不能直接合并执行器 |
| 4：共享 SDK | 薄 SDK、退出只解绑、显式重连，符合职责 | SDK/MCP/CLI 重复组装任务请求和结果查询；低层 Device 使用方尚未迁移 |
| 5：调试命令 | 复用 registers/peripheral_watch/hardfault/debug_control；保持只读与暂停语义区别 | debug_api 同时包含 HTTP 与业务操作；新增实现不宜继续堆到 REST 文件；旧 MCP 同类实现还在 |
| 6：真实 WebGUI 修复 | RTT 停止成功后才更新 UI；拒绝时保留显示；释放后同步状态；按USB重连 | 属于正确的状态提交顺序，不是应删除的“补丁”。但 AXF 恢复、窗口缓存和会话符号一致性仍分散 |
| 7：恢复提示 | 区分网络不可达与401，标记旧数据，浏览器只提供重新检查 | 正常重启恢复证据有限；不能外推到强杀、休眠、拔插；重复健康状态最终应收敛成明确状态模型 |

## 实质问题及优先级

### A1 · P1 · 独占写操作有第二条执行入口（本轮已修）

证据：`runtime_jobs.py:PATHS/execute` 和 `runtime_api.py:RuntimeGate`。
GUI/CLI/MCP 正常流程提交任务，但持令牌的调用者可直接 POST `/api/device/flash`、
`erase`、`reset`，空闲时旧处理器仍会执行，绕过确认、request_id、日志及去重。
“GUI 走新入口”不能证明旧入口已删除。

本轮使共享模式下这三个执行路由仅接受当前任务的内部调用，入口仍集中到现有
RuntimeJobs，没有新建第三套任务。任务本身继续复用原算法。非共享服务不在此次改动范围。

### A2 · P1 · 两套退出规则发生语义分叉（本轮已修）

证据：`runtime_api.py:install_runtime.stop` 与 `runtime_management.py:stop_backend`。
管理页拒绝在采集运行或其他窗口存在时退出；旧 `/_runtime/stop` 只检查 AI/CLI/SDK
会话和正在执行的命令。GUI 独自采集且没有这些会话时，CLI 可以直接关闭后台。

本轮两个入口调用同一个退出策略，共享确认、忙状态、会话、窗口和采集检查。退出
整个进程仍须检查所有采集，包括独立 UART/Modbus；不能把“设备释放”和“进程退出”混为一谈。

### A3 · P1 · 资源分类重复造成误互斥（本轮已修目标读写/任务/释放范围）

证据：RuntimeGate、RuntimeJobs 原先遍历所有 `get_managers()`；已有
`dashboards.py:BRIDGE_DASHBOARD_TYPES` 已准确区分 CDC 采集与独立串口资源。
结果是串口助手或 Modbus 正在采集，也会使 MCU 内存读取、任务提交或释放 CDC 失败。

本轮复用既有分类与一个查询函数，删除共享层自己维护的 CDC 列表及“所有采集都占CDC”
的判断。独立串口资源继续由原 ResourceManager 和端口锁管理，不再新增锁体系。
串口/Modbus 的全部路由仍被中间件粗粒度分类，这部分需要服务准入重构和物理串口验收。

### A4 · P2 · 窗口生命周期重复（本轮已去掉共享页面的旧握手）

证据：`App.vue` 同时调用 `startBrowserSessionLease` 和 `startSharedRuntimeView`；
共享后台没有启用旧 browser session lease，仍接到一次无效 WebSocket 握手和退出请求。
本轮等待健康检查确认模式后，仅启动对应窗口机制，同实例短暂离线不重复注册。
旧租约仍供非共享服务使用，不能在未核对其用户前整文件删除。

另一个待修问题：`sharedRuntimeView.ts` 在 pagehide 永久 stop，未处理 bfcache 的
pageshow 恢复。源代码已确认缺口，尚未做浏览器往返缓存复现，本轮没有宣称它通过。

### A5 · P1 · 内部自动重载绕过共享准入，符号只绑定路径（后续收敛已实现）

证据：`remote/api.py:check_file_sources` 从定时任务直接进入
`_exclusive_probe_control`，后者会 `stop_bridge_dashboards` 再解析符号；
`runtime_api.py:Session/call` 只记录/比较 axf_path。此路径不经过外部 HTTP 的
operation_lock、订阅检查和独占任务准入。

同一路径 AXF 重新编译时，可能在 AI 订阅或任务运行期间停止采集/更换符号；文件路径
没变也不足以告知现有会话布局已经变化。此为源码确认的设计缺口，未对真机进行这种
并发故障注入。不能通过在 RuntimeGate 增加一个路径解决，因为没有对应外部请求。

下一步应让文件监控只产生“内容变化”事件，交给公共应用服务处理。先判断当前任务、
采集和会话，再作受控重载；保留待处理变化，不能在忙时把变化消费掉。共享会话应绑定
符号版本/指纹，而非仅文件名。使用现有 SourceMonitor、SymbolCatalog 指纹和目标租约，
不另写文件监控或符号解析器。

后续收敛将 HTTP 和 SourceMonitor 的执行交给 `RuntimeControl.run_operation`，
复用原操作锁、取消等待和操作记录。文件变化保留到成功处理，任务、连接、会话或 CDC
采集忙时延后；手动符号更新也检查会话和采集。会话绑定已有 SymbolCatalog 的
generation 和 SHA-256，调用及任务提交验证版本，显式重新附着才接受新版本。
RTT 等待提示不会清空地址或断开数据订阅。验证与边界见
[符号重载收敛报告](v0.3.0-shared-symbol-reload.md)。这一步不表示所有 REST 资源策略
已经迁出 RuntimeGate，A6/A7 仍须继续处理。

### A6 · P2 · MCP 双实现及能力目录尚未迁移完

证据：新入口 `cli._cli_mcp → runtime_mcp.run`，但旧 `mcp_server.py` 仍有完整
Device 操作实现、build_server/run 公共导出、atexit 清理及大量测试。
新 MCP 为复用一个 `_isolate_stdio_protocol` 辅助函数而导入整份旧服务器。
因此“删除 --direct”并不等于“旧独占实现已经全部删除”。

建议先把通用 stdio 辅助函数移到中性模块，盘点新旧工具及调用方，然后将保留的操作
改成共享适配，最后删除失去调用者的旧实现/专属测试。不要为删文件而丢失尚未迁移的
供电、安全操作、调试速度、观测等契约。`remote/capabilities.py` 的 schema/risk 信息
可复用，但远程操作名、编码、确认语义与本地 HTTP 表不同，不宜直接机械合并字典。

### A7 · P2 · 跨进程锁和测试门禁仍有边界

`runtime.py` 给后台设置独立 TEMP；`local_resources.serial_lock_path` 仍由 TEMP
定位建议锁。同一串口的不同进程可能看到不同锁文件，资源盘点/释放也可能漏掉后台。
Windows 串口句柄自身仍提供独占，不能据此断言已经发生双开；跨接口 CMSIS-DAP 也
不能靠串口锁替代。应把探针资源租约放到稳定的用户数据目录，和临时文件目录分开。

`.github/workflows/feedback-checks.yml` 仍只跑反馈队列和 Skill 边界测试。CI 绿色
不能当作共享架构回归已运行。大量旧 MCP 单测通过也不能代替当前 runtime_mcp 的契约
验收。需要增加共享准入、任务、身份、适配器与关键 GUI 测试门禁，私有 FLM/HIL 单独列证据。

## 不应误删的分层

- startup/owner 文件锁、请求 operation_lock、ResourceManager、Bridge 命令锁分别
  管理进程唯一性、请求生命周期、目标资源和字节流，它们不是同一把锁的复制。
  需要统一策略和固定获取顺序，不能为“减少锁”简单删除其中一层。
- Session 的 TTL 与 GUI window presence 服务不同生命周期。前者绑定工程、符号和
  采集订阅，后者只是窗口存在性。应复用生命周期实现，不能让关闭窗口等价于结束后台。
- RuntimeJobs 提供 CDC 操作日志/去重；OnlineFlashJobManager 有 pyOCD、进度、取消
  和阶段状态。可以统一公共任务记录/状态外观，不应把不同执行器硬拼成一个线程模型。
- 无暂停 fault_snapshot 与自动暂停的详细 HardFault 分析不是等价操作。可以共用
  采样/解码服务，但必须保留对目标运行状态的明确语义。
- 第六轮“成功后更新前端状态”、第七轮“失联标记旧数据”都是必要一致性修复，应该保留。

## 收敛目标与推进顺序

目标调用链为 `GUI/CLI/MCP/Remote适配器 → 应用服务 → 既有资源/任务/采集层 → Device/Bridge`。
认证留在 HTTP/WS 边界；工程/符号版本、确认、任务/采集冲突和硬件执行归应用服务。
内部监控与外部入口调用同一服务。能力契约包含参数、资源、结果及风险元数据，适配器
只转换协议，不自行决定是否抢占、重连或重试。

1. **先堵内部边界**：为符号重载和独占操作提取公共准入；验证内容变化与任务、AI 订阅
   交错时不抢停、不换布局、不丢待处理事件。补符号版本绑定。
2. **再消除迁移残留**：统一能力契约与 SDK 任务请求；逐项迁移旧 MCP、专用 CLI 和
   低层 Device 调用者，再删除旧实现。给新增路由/后台任务加“必须声明资源策略”的测试。
3. **补稳定性基础**：稳定用户目录锁、bfcache、重启/版本握手、日志轮转、CI 契约门禁。
   不为这些问题引入新的消息总线、通用插件系统或第三套任务管理器。
4. **再验收交付**：WebGUI 与双设备长稳、操作中拔插/休眠、全新连接 erase 和脱机部署，
   然后 NSIS 安装升级。WinUSB 和探针固件继续保持原计划，当前不需要新增固件别名。
