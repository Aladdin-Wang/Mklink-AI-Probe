# STM32F103 ARM mem_dump qualification — 2026-09-13

## Scope and outcome

STM32F103 high-density device (DBGMCU DEV_ID 0x414), 512 KiB Flash, 64 KiB RAM, 72 MHz RT-Thread 5.1.0 target. Board identified by its owner as STM32F103RET6; shared SWD ID alone does not establish exact ordering code. Application starts at 0x08005000.

**4/10 MHz passed the bounded tests below; 20/30 MHz did not pass and remain rejected for ARM.** This is one board and wiring setup, not qualification of all ARM chips. No RTT throughput, mem_read or mem_write throughput benchmark was run.

Stable probe UF2 SHA256: `5436f6e4164140916d2171027600a6ea7c7b5d5bb546e50a727a15031f4d6fdf`.
Performance target BIN SHA256: `c7d47098ff312d676ae0335a971d5fcf17f533e4f2cd367b1d87a170362254af`.
Independent functional-demo BIN: `6a0212f5697ad86fae0fd7751241e095cb8003e709812b448f240ba58707590d`; demo enables PID/HardFault/RTT tasks omitted from the performance build. Do not mix their AXF files or addresses.

## Firmware change

A fixed, aligned 32-bit RAM/Flash address uses a 24-record firmware batch: configure AP CSW without increment, set TAR once, prime posted AP DRW, then drain the final value with DP RDBUFF. Every requested sample corresponds to one target read. Per-record probe timestamps and existing USB framing/CRC remain. Unsupported layouts use the existing memory path; MMIO is excluded from this fast path. WAIT responses retain bounded retries; parity/fault/exhaustion fail the batch instead of publishing uncertain values.

Compiled C model: counts 1..24, posted-read order, final drain, record guards and failure injection at every transfer passed. Compiled RV32 shift model: 268 patterns passed, but the experimental electrical path failed the real board. That path is disabled by default. Software timing models do not establish electrical reliability.

## Measured clocks and high-speed failures

Kingst LA5032, 500 MSa/s, SWCLK CH2/SWDIO CH1. Clocks below measure parity-valid read-data bit periods, excluding header, turnaround, WAIT and packet gaps. They are not uniform transaction clocks.

| Requested | Read-data clock | Outcome |
|---|---:|---|
| 4 MHz | 3.904 MHz | Stable candidate passed |
| 10 MHz | 10.549 MHz | Stable candidate passed |
| 20 MHz | 19.853 MHz | Experimental shift: parity error after 648 valid samples |
| 30 MHz | 29.620 MHz | Experimental shift: no valid mem_dump sample; parity errors |

An earlier 20 MHz kernel actually ran at 22.31 MHz. Calibrating it to 19.85 MHz and moving its sampling point did not qualify the link; an early sampling experiment even shifted the ID value. These failed trials are retained separately. The available digital capture does not establish an analog signal-integrity root cause. Stable firmware rejects SWD clocks >=20 MHz without changing the selected clock; host SDK/CLI/MCP/Web keep their ARM high-speed guard.

## Comparison with the old firmware

Old nominal 10 MHz ran at approximately 11.16 MHz and delivered 39.619 kSa/s single RAM. Posted batching with that same old timing reached 117.321 kSa/s in a separate five-second test; the stable calibrated version delivers 101.293 kSa/s at 10.549 MHz (about 2.56× old end-to-end throughput despite slower clock). These are distinct candidates, not interchangeable stability claims.

Large blocks and multiple independent addresses do not use the fixed-address fast path. Old nominal 10 MHz 4 KiB RAM was 173.37 blocks/s versus 157.59 now; calibration reduced its clock, so **no large-block speedup is claimed**. Single-address p99 remains above median because batching/USB scheduling adds gaps; the per-record timestamps preserve those gaps, rather than assuming equally spaced samples.

Shared profile tests: 27 passed, including exact SWD acknowledgements, legacy mode and mismatch/rejection. JTAG profile handling remains covered by the same tests.


## Actual host and GUI checks

Actual SDK and CLI low/medium calls returned confirmed SWD profiles. Actual MCP stdio connected to the board, confirmed low/medium, rejected high/ultra and disconnected. Chrome likewise applied low/medium and rejected high/ultra. The GUI single-variable view on the functional demo showed 100,852.45 Hz with a 10 µs requested interval, while the three-variable PID view ran at the requested 1 ms interval. These GUI observations are separate from the performance-build matrix above.

Functional-demo A was compiled with Keil AC6 with zero warnings/errors and downloaded with Verify OK. Chrome showed a simulated PID setpoint/feedback/output trace, RTT live output, RAM write/read/restore and two SystemView sessions with 14 tasks at 72 MHz. The first trace included one historical target overflow marker; after its baseline there were no new target drops. The second trace showed no target overflow marker. Runtime/parser/transport drop counters were zero. A deliberate UDF in the demo task was decoded as UNDEFINSTR/FORCED, exact PC 0x0801289C at applications/main.c:145; MCU reset and a second check returned no HardFault. Stack-scanned caller candidates remain inferred, not exact.

RTT bidirectional testing exposed two target-side consumers of RTT channel 0 (demo rttrx and RT-Thread console). Demo B removes the duplicate rttrx task, leaving the console as the sole reader. Its BIN SHA256 is `16c5e4fe438f47cf4041b6f5c137183816bb1b823a5684576b50dd0ca7179015`. Keil rebuild/download passed, and Chrome help/version commands with CRLF returned the complete RT-Thread shell response and version 5.1.0. Demo A screenshots retain their A-build attribution; B has one fewer task. No new RTT throughput claim is made.

The GUI retains a stale symbol-reload advisory after restarting acquisition; the running status, observed curve and counters establish the current acquisition state. This display issue has not been fixed in this change. Offline/option-byte workflows have separate prior qualification reports and were not re-qualified in this matrix. UART/Modbus physical links were not exercised.
