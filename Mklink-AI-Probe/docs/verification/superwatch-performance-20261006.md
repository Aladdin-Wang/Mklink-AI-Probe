# SuperWatch 性能修复与影响评估

## 范围与结论

本轮修复 CDC 多路复用路径的采样性能退化，不增加 WinUSB，不修改 SDK、
Arm-2D 或 MicroBoot。两台 V4 已升级同一候选固件；这是开发分支短时验证，
不代表发布、全功能重新验收或长期稳定性通过。

最初安装态三变量采集约 198.5 Hz。发现主机最短 2 ms 限制、固件每个区域
等待 RTOS tick、无 RTT 时仍交替空转、分组结束后再次等待间隔，以及未复用
原有批量 SWD/JTAG 读取内核等问题。不能把三变量原始结果与单变量峰值直接
计算为同条件提速倍数。

## 修改与兼容性

- `usb2variable.c` 与多路复用共用 20 μs 分界。低于 20 μs 全速，
  20 μs 及以上按设定间隔采样；总吞吐仍包含总线、编码、USB 和调度开销。
- HELLO 能力位 4 协商微秒命令 `0x32` 和紧凑采样批次。老固件仍走 `0x30`
  毫秒协议；请求/响应上限仍为 256 B，只有协商后的 Watch 事件可达 1024 B。
- 单个对齐 4 B 变量复用既有 SWD/JTAG 批量内核；多区域继续使用通用路径。
  时间戳使用目标采样完成时钟，主机处理 32 位回绕。
- RTT 各通道按 1 ms 到期轮询，不以空 RTT 轮次限速 Watch。
- DAP 保持最高优先级。SWD/JTAG 在安全事务边界结束批次并排空流水线，
  再交还目标锁；DAP 改变目标后旧采集失效，需要显式重新开始。
- 显示线程优先级 25，采集控制线程 23，USB 服务 22；屏幕刷新排在后面。
  快速采集每 100 ms 留一个 tick 给低优先级维护，不等待刷新完成。
- CRC 表和样本池复用原有静态空间，不新建线程或堆分配。

## 历史证据复核与差异定位

用户提供的 MicroBoot 文档中，`docs/assets/examples/stm32f103-rt-thread/
r21-crc-prefix/README.md` 及两个原始 JSON 明确区分持续、主机接收和批内速率。
`30M-20s-201k.json` 的实际持续值为 201,741.84 Sa/s、主机 201,288.78 Sa/s、
批内 282,345.37 Sa/s；120 秒记录持续 193,449.39 Sa/s。两者均预热 200 ms，
持续速率包含全部批间间隙，间隔中位数 3 μs，最大间隙分别 312/339 μs。
因此上一轮达到约 156 kHz 不能认定性能已经恢复。

HPM5301 历史 `docs/mklink/hpm/mem-dump-profiles.md` 的后续资格记录约
98.4–100 kSa/s；高频实验短测约 109 kSa/s。HPM6E80 的 113 kSa/s、三变量
42.8 kgroup/s 来自另一块芯片，不能直接作为当前 HPM5301 的同条件结果。
STM32 历史目标是纯正弦测试程序，当前为八通道 RTT 测试程序，目标程序负载
与 RAM 地址不同；这部分影响没有被历史数据单独隔离。

### 当前固件的同条件协议对照

每块板单独进程绑定探针；首次脚本跨探针绑定被身份保护拒绝，HPM 改为独立

### 已定位的路径缺失与待隔离成本

1. **多变量未接入既有批量内核，已由代码和同镜像对照确认。**
   `mux_runtime.c::fast_watch()` 只接受一个 4 B 区域。其他布局逐区域执行
   `read_mem()`、封包和调度；JTAG 调用普通 `riscv_debug_sysbus_read_mem()`，
   没有复用历史多地址 SBA 批流水线。旧 `dump_try_batch()` 支持 16 个字、
   共 64 B 的 JTAG 批量采集。HPM 四区域约九倍差距不能归因于 GUI 绘图。
   STM32 旧批内核本身只加速单字；连续 16 B 与四区域也不能混作同一个基线。

2. **公共路径的体积优化影响了热点，成本显著但单因果实验尚未完成。**
   提交 `58c47a9` 为 `usb2variable.c` 加入整文件 `#pragma GCC optimize("Os")`；
   `usb2console.c`、`mux_runtime.c`、`mux_protocol.c` 也使用体积优化。
   项目默认原为 O3，高频代码随之一起改变，不能只视为冷代码瘦身。
   当前 STM32 旧协议追加 5 秒诊断为 141.85 kSa/s：64 点一批的采集/封包/
   批间间隔平均为 277.57/135.42/174.42 μs，历史 r21 20 秒记录为
   240.10/60.68/77.25 μs。批间间隔已含封包和排队，不能重复相加。
   封包差值约 74.7 μs/批，是明显待恢复开销；目标负载、编译和其他变化仍需
   分别控制，不能把全部差值都算到 Os。当前多路复用每样本采集/封包分别为
   STM32 4.83/1.37 μs、HPM5301 8.67/1.62 μs，说明更短报文并未自动变快。

3. **高频代码布局和每样本调用需要收敛。**
   当前 map 中旧定长封包位于 ILM，但新事件封包、CRC、时钟回调及 DAP
   保留检查在 Flash。SWD 旧接口如今包装新的通用定时内核，循环含运行时
   定时分支；多路复用还在每样本调用 DAP 检查。此处是确定的代码差异，
   每项实际耗时尚未单独测量。必须保留 DAP 安全边界检查，不能靠取消保护
   恢复峰值，也不能在 RAM 不足时把整个模块机械搬入 ILM。

4. **USB 背压退让放大间隙，调度路径已确认，间隙占比待测。**
   `usb2console.c` 在 `mux_session.pending` 时直接 `rt_thread_delay(1)`；
   即使 USB 稍后已腾出空间，也要等待调度恢复。另有每 100 ms 一次 tick
   维护退让。短测确实出现毫秒级间隙，但还没有逐次关联 USB 背压、维护和
   其他中断，所以不能把每一个间隙都归因于同一种原因。屏幕保持低优先级；
   改善方向是传输就绪唤醒、有界维护，而不是删除必要维护或提高显示优先级。

尝试用哈希匹配的历史 r21 UF2（`f28c012e…406cd`）在同一 STM32 下载器
补做整镜像 A/B，但旧镜像在 45 秒内未返回运行盘，未获得历史镜像的新实测。
恢复块正常执行，重新写回当前 `b542c669…dee3`，运行盘、版本及多路复用
能力重新验证通过。目标板程序未改；启动失败原因尚未定位，不用它推断性能。

### 后续修复顺序与验收口径

先把采样、时间戳转换、封包、CRC 和 USB 拷贝从整文件体积优化中分离，
做小范围编译/存放位置 A/B；再让多变量复用现有多地址批处理及有界分组帧，
避免新造第二套 SWD/JTAG 内核。然后测量并改善 USB 背压唤醒，保留 DAP
抢占、20 μs 分界、RTT 1 ms 和屏幕最低优先级要求。

每一步都要记录相同目标镜像/地址/调试档位/布局、持续与主机速率、完整组、
CRC/丢失/间隙以及 RAM/ILM/Flash 成本。峰值恢复后再验证 RTT 八路共存和
DAP 烧录/仿真；不能用单变量峰值替代多变量、完整 GUI 或优先级验收。
本次完成差异定位，未将上述候选修复冒充已实施或验收；长稳仍按用户要求延后。


## 2026-10-06 性能修复与 OpenOCD 抢占复验

本节替代上节“尚未实施”的状态。按用户要求，新主机与新固件配套升级，
删除旧毫秒命令和旧单字批帧兼容分支；仍使用 CDC，不新增 WinUSB 接口。
第三方串口助手的透明 RTT 保留。

### 根因与收敛

- 多变量复用既有 JTAG 多地址 SBA 批内核；SWD 连续普通 RAM/Flash 复用
  既有块读取。统一 status=9 帧携带完整采样组，最多 64 B/组，按容量限制批长。
  非对齐或更大区域继续使用有界普通读取，不降低原来的 15×128 B 容量。
- 采样、时间戳、封包、CRC、USB 拷贝恢复热点速度优化；SDK 内联时钟函数
  不再被文件级 Os 连带降级。冷路径继续节省空间。
- 最明显的单项 A/B：仅将命令/采集线程的原有 4096 B 栈从 AHB 移回 ILM，
  STM32 从 162.81k 提升到 206.08k，HPM 从 86.66k 提升到 113.45k（各 3 秒）。
  显示线程原有 6144 B 栈移至 AHB，优先级仍最低；不修改 Arm2D/SDK。
- USB 满缓冲时等待完成中断唤醒，避免固定 1 tick 背压等待。保留 DAP
  预留/互斥检查、RTT 每通道 1 ms、每 100 ms 一次维护退让。
- OpenOCD 实测发现 JTAG 退出后未恢复引脚/DM；提取已有非复位初始化，
  与 SWD 共用一次性恢复入口，不自动续用旧 RTT 游标，不复位/恢复运行目标。
  普通 RTT 适配器继续要求目标处于运行状态。

### 最终候选吞吐

同目标镜像、30 MHz 档位、同地址、0.2 秒预热、3 秒测量；无 RTT、GUI，
测量窗口内不插入普通命令。以下使用目标时间戳计算完整组持续率。

| 目标/布局 | 修复前 MUX | 修复后 MUX | 比值 |
|---|---:|---:|---:|
| STM32 单个 4 B | 149.94k | 208.23k | 1.39× |
| STM32 连续 16 B | 13.55k | 24.01k | 1.77× |
| STM32 四个 4 B 区域 | 4.35k | 24.07k | 5.53× |
| HPM5301 单个 4 B | 86.13k | 114.71k | 1.33× |
| HPM5301 连续 16 B | 6.25k | 33.53k | 5.37× |
| HPM5301 四个 4 B 区域 | 3.19k | 33.53k | 10.51× |

多字布局的单位是完整组/秒，不能将它直接写成每变量独立采样频率。
六项均无 CRC 错误、解析丢帧、固件错误标志或不完整组。
JTAG 恢复修复前、采样热路径相同的候选另做了 20 秒单变量测量：
STM32 193.16k、HPM5301 111.41k；主机接收率分别 192.37k、111.81k。
该结果接近/达到历史持续率量级，不能保证任何负载持续 200k。
20 秒计数器的 32 位 CPU 周期累计已回卷，不能用其计算采集阶段平均成本。

1/19 μs 均全速；20/21/100 μs 间隔中位数分别是 20/21/100 μs。
包含普通命令的短测平均速率分别约 42.69k/40.67k/9.74k，受到批间传输和
调度影响，并不是理想的 50k/47.62k/10k。最大片间隙仍约 1.1–1.4 ms；
此方案保证 DAP 优先而非硬实时等间隔，不掩盖间隙或补造样本。

### 正确性与抢占

- STM32 Flash 常量/HPM 固定测试数组只读逐字节比较，共 56 个配置：
  单字、64 B、15 个稀疏区域、乱序混合大小、奇地址、128 B、15×128 B；
  分别设 1/20/100/1001 μs。无数据混组、时戳倒退或主机事件丢失。
- STM32 RTT 0–7 均收数据，每路发送 256 B 并核对目标累计数量与哈希。
  与 SuperWatch 并行时，pyOCD 单步/APP 真实扇区烧录/全段读回通过，
  0x08005000 以下 Bootloader 不变。调试期间 MUX 内存操作返回 busy，
  旧 RTT/Watch 明确失效，退出后显式重启采集成功。
- **OpenOCD 真实验证**：STM32 0.11.0+dev 配套脚本、HPM 0.12.0+dev；
  使用探针现有 CMSIS-DAPv2 bulk 接口和唯一序列号选择，未增加 USB 接口。
  在采集中连接约 0.27 秒后已暂停目标（包含进程/USB 初始化，不是固件仲裁延时）；
  单步、运行/暂停、擦除写入、verify_image、退出后重启采集均通过。
  STM32 为 RTT 八路+Watch，HPM 目标程序仅 RTT0 出数+Watch。
  STM32 写入/校验 113304 B，Bootloader 20480 B 前后相同；
  HPM 校验 ELF 有效数据 38508 B。调试抢占后旧采集失效期间会丢弃有界主机积压，
  不能把该场景描述为无损连续采集。
- 最初尝试本机 HPM OpenOCD 0.12 工具包的 STM32 脚本，发现它仍调用已移除的
