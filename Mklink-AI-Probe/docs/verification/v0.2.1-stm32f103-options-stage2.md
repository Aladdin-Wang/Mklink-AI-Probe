# STM32F103 选项字节配置第二阶段

2026-09-11，开发分支 `codex/v0.2.1-development`，提交既有 PR #2。

## 功能范围

CLI、MCP、脱机烧录页面共用字段描述、输入校验和脚本生成器。STM32F103 非 XL 容量组在 V3/V4 上开放 USER 的 WDG_SW、nRST_STOP、nRST_STDBY，DATA0/1 和 WRP0..3。RDP 保留原有安全配方入口，不接受通过 `option_bytes` 设置原始读保护值。其他 ARM 系列及 HPM 的既有能力不变。

页面分别展示存储值、影子值和配置目标。留空表示保持每块板自己的当前值，可以只部署选项配置，也可以与固件烧录组合。WRP 按容量解释有效位、页范围及高容量组最后一位覆盖范围。XL 型号、未验证执行接口及无效字段不能生成新配置脚本。

```sh
python -m mklink configuration describe --chip STM32F103xE --model V4
python -m mklink configuration read --chip STM32F103xE --port <console-port>
python -m mklink configuration generate --chip STM32F103xE --set DATA0=0x5A
```

MCP 对应 `configuration_description`、`read_configuration`、`configuration_script`。生成接口只返回配置与脚本，不自动连接或烧录；Web 的预览、部署及触发继续复用现有脱机接口。

## 执行与校验

芯片布局依据 [ST PM0075](https://www.st.com.cn/resource/en/programming_manual/pm0075-stm32f10xxx-flash-memory-microcontrollers-stmicroelectronics.pdf)。脚本运行时核对器件组、Flash 容量、RDP 未保护状态、互补字节和影子寄存器，再合并所选字段；保留其余字段与保留位。组合任务在上述检查通过后才烧录固件，随后写选项。固件步骤失败时不会继续写选项。

选项 FLM 使用既有可信资产，生成和部署均校验 SHA-256，用户固件算法不能覆盖其文件名。脚本只写 16 字节选项区域，原始 RDP 保持未保护。先回读存储，再系统复位，再核对存储和影子；只有全部匹配才输出 `MKLINK_OPTIONS_VERIFIED`。无变化输出 `MKLINK_OPTIONS_UNCHANGED`，不调用选项擦写。配置任务不切换目标供电，不执行 RDP 转换。

## 旧固件兼容问题及处理

实际使用的探针报告 V4.3.9。本轮未修改或更新下载器固件。

- 原生 `load.bin` 拒绝过短输入；单记录的 16 字节 HEX 又会被 `flash_decoder_write` 缓存而未编程，`load.hex` 忽略关闭阶段失败后仍报告成功。实际测试由新增回读校验检测到未写入。生成器采用两条同址、同内容的 16 字节 HEX 数据记录，触发旧解码器初始化；绝不通过越界填充扩大选项写入范围。
- 分别调用原生擦除和编程命令会分别初始化目标并复位，不能在选项已擦除而 RDP 尚未恢复时拆开执行。当前使用同一次 `load.hex` 内的擦写会话。
- 大脚本触发过堆内存不足；含函数的脚本还会进入 Pika 字节码缓存。嵌套函数实验曾断开 USB，源码控制台栈为 6 KiB，栈不足只是候选原因，未做栈水位测量。
- Pika 的布尔表达式不能假定短路，嵌套循环 `continue`/`break` 实测也出现迭代器错误或提前退出。最终事务使用共享读取循环和状态控制，不生成函数或事务内部跳转；组合下载不重复展开事务。最终版本的连续写入与恢复均完成，不需要在成功的事务之间重启探针。

固件后续宜修复短数据结束时的刷新、传播 `close_bin/close_hex` 错误，并提供一次目标会话内的专用选项事务接口。不能把原生“loaded success”单独作为选项写入成功依据。

## 验证结果

板卡为用户接入的 STM32F103，实读属于高容量组、512 KiB。该证据不能确定完整封装订货号；测试使用 xE 容量描述，Chrome 从目录选择同容量 STM32F103RE。用户给出的 RC 工程目录不作为芯片容量依据。

| 验证 | 结果 |
| --- | --- |
| 描述、原始值、影子值 | CLI、真实 MCP stdio、Chrome 的 10 个字段一致 |
| DATA0/1 | 改为 0x5A/0xA5，复位后双重回读匹配，再恢复 |
| nRST_STOP / nRST_STDBY | 两位由 1 改为 0，复位回读，再恢复为 1 |
| WRP3 | 由 0xFF 改为 0x7F，复位回读，再恢复为 0xFF |
| Chrome 实际操作 | 无固件文件，输入 DATA0、预览/部署/触发、读取，再配置回原值；页面错误为零 |
| 组合下载 | 先重烧与备份完全相同的首个 2 KiB Flash 页，再设置 DATA0；两步成功并通过选项复位校验 |
| 最终恢复 | 所有原始选项恢复；全部 512 KiB Flash 的 SHA-256 与事前备份一致 |
| 自动化 | 99 项 Python、29 项 GUI 测试通过，生产构建通过 |

Python 测试执行生成事务，覆盖错误身份/容量、短读、RDP、互补值/影子错误、无变化、写入后错误、复位后错误、字段保留、算法篡改以及固件失败后禁止写选项；另验证 CLI/MCP/Web 生成相同脚本。GUI 测试覆盖编辑、清空恢复保持、纯配置部署和型号切换失效；真实浏览器发现的旧型号搜索覆盖新结果问题已修复，并以延迟响应测试和最终 Chrome 回读验证。

## 边界与现场状态

本轮验证的是配置写入和复位加载；未进入 STOP/STANDBY 验证低功耗行为，未启用硬件看门狗，未通过故意编程受保护 Flash 验证 WRP 拒写。未进行 RDP 保护切换，也没有 V3、其他容量板卡或其他 ARM 系列的新增实板证据。

最终目标选项与程序恢复原状。源码 Web 验证使用本机 8766 端口；原有 8765 服务没有被终止。目标程序无需修改，因此未改变用户提供的测试工程。正式安装器、全局 Skill 和发布通道没有更新。
