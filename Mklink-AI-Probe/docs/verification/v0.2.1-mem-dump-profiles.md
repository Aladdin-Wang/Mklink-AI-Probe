# HPM5301 mem_dump profiles and host pause tolerance

Date: 2026-09-12. This qualification uses one MKLink V4 and one running HPM5301 target. No target firmware or target RAM writes were performed. RTT and ordinary mem_read/mem_write benchmarks were explicitly excluded.

The exact tested probe UF2 SHA-256 is `4675eeafb1cf8145dd8aba7fed50e257ac57931d84cc25f009b56de857fd8a4e` (1,555,968 bytes). The target image stayed unchanged. A later ILM experiment was reverted and the exact same qualified UF2 was restored.

## Configuration and common interfaces

- Low: 4 MHz; medium: 10 MHz (new HPM connection default); high: 20 MHz. SuperWatch exposes these three choices above the waveform. Applying a profile stops an active dashboard stream first. The selected Web profile is saved and reapplied on connection.
- REST: GET/POST `/api/device/debug-speed`; POST body `{"profile":"high"}`. SDK: `device.set_debug_speed("high")`. CLI: `python -m mklink debug-speed high --port <port>` (`--save` persists the choice). MCP: `set_debug_speed(profile="high")` retains the choice within its connected session.
- CLI periodic measurement: `python -m mklink dump-benchmark --port <port> --speed high --duration 3 0x00080500:4`. Existing `dump-memory` also accepts `--speed`. MCP: `measure_dump_memory(regions=[{"address":525568,"size":4}], duration=3, speed_profile="high")`. This returns rates/intervals/integrity without any GUI. MCP `dump_memory` retains bounded snapshot behavior and accepts an optional `speed_profile`.
- Measurements allow 1–15 regions, at most 4096 payload bytes, 0.5–30 seconds. They use complete samples and the probe timestamps, with 200 ms warmup excluded. For B1, blocks have different timestamps; the first block timestamp represents the complete assembled sample. CRC, sample flags, block order and byte coverage are checked.
- High speed requires HPM5301 and explicit matching firmware profile acknowledgement. Unsupported high speed is never mislabeled as qualified. Old HPM firmware can retain unqualified legacy low/medium timing. ARM high speed remains disabled pending separate physical validation; the HPM results do not qualify ARM.

## Comparison with the supplied reference

The supplied table uses an HPM6200EVK probe and HPM6800EVK target with different wiring. Its fixed-address sampling implementation and error-checking semantics have not been supplied. These are comparisons of reported outcomes, not proof of equivalent workloads.

| Metric | Our 10 MHz | Reference 10 MHz | Our 20 MHz | Reference 20 MHz |
|---|---:|---:|---:|---:|
| Fixed 4 B | 31.842 kSa/s (41.5%) | 76.7 kSa/s | 45.875 kSa/s (30.8%) | 148.74 kSa/s |
| 4096 B periodic payload vs reference SBA stream | 0.513 MiB/s (83.0%) | 0.618 MiB/s | 0.816 MiB/s (64.6%) | 1.263 MiB/s |

A warmed 4-byte sample still uses four DMI scans: explicit address write, data read, SBCS read, and NOP collecting SBCS. At 20 MHz, 4 × 41 shifted bits alone require 8.2 µs; TAP edges, function processing, CRC and USB framing add more. Thus this transaction organization cannot achieve the reference 6.724 µs/sample (148.74 kSa/s). Fixed-address auto-read, cross-sample pipelining and batched validation are candidates, not verified explanations of the reference.

The next useful reference sources are the fixed-4B periodic sampling loop, SBA/DMI helpers, sample timestamps, busy/error recovery, USB queues, and the measurement script. Existing local reference code primarily contains low-level JTAG kernels. We will not remove error checks or silently label prefetched old values with current timestamps to improve the displayed frequency.

## Integrity and long intervals

All three profiles matched the entire 63,344-byte target Flash image via binary dump, plus 12 aligned/unaligned/boundary cases. A separate known bit31=1 word was captured with the logic analyzer in each profile. The 20 MHz CPU bit31 fault was fixed by retaining the bit-zero shift instruction in the packed second word; merely widening the high phase did not fix it.

Each profile also ran 30-second single- and dual-channel SuperWatch acquisition tests using the same mem_dump backend. Results (rate / p99 / maximum interval):

| Profile | Single channel | Two channels |
|---|---:|---:|
| 4 MHz | 17.703 kSa/s / 134 µs / 259 µs | 12.298 kSa/s / 166 µs / 285 µs |
| 10 MHz | 32.870 kSa/s / 97 µs / 230 µs | 22.868 kSa/s / 121 µs / 255 µs |
| 20 MHz | 47.848 kSa/s / 80 µs / 219 µs | 34.274 kSa/s / 92 µs / 4361 µs |

One 20 MHz dual-channel run contained a 4.361 ms outlier with maximum USB IN duration 4.215 ms; queue-full and error counters remained zero. Its precise cause is unresolved. A later 30-second raw dual-channel retest produced 1,055,097 frames, 35.272 kSa/s, p99 95 µs, maximum 226 µs, zero frame errors and zero USB queue-full events. The outlier is retained as a limit; this is not a hard real-time guarantee.

The reproduced 150 ms application-reader pause formerly caused a 135.999 ms sample gap and 132 USB queue-full events at the same 15 MHz trial timing. Moving the Windows serial reader into an independent process reduced that controlled test to a 225 µs maximum gap and zero queue-full events. On final 20 MHz firmware, a forced 150 ms parent GIL hold gave 171,653 valid samples, p99 82 µs, maximum 224 µs, and zero new USB queue-full events. This fixes bounded application-pause tolerance, not arbitrary OS stalls. The host buffer remains finite. The worker is enabled for normal Windows Python runtimes; frozen executables and other OSes retain the existing receiver and are not qualified by this result.

Moving the entire SBA stream state machine into ILM raised 20 MHz single-word throughput only from 45.875 to 45.912 kSa/s, and 4096-byte throughput by about 1%. This experiment was reverted to preserve approximately 3 KiB ILM. Final ILM unused is 5,122 bytes.

## Verification and remaining gates

- Firmware host model: 5232 real SES-assembled RV32 scan cases, including all 41 bits, TAP/idle transitions, GPIO masks, IRQ and ABI. SBA model: five configurations covering bounds, cleanup, sticky/busy faults and rollback.
- Application: 121 Python tests passed, 1 skipped; 29 GUI component tests passed; production frontend build passed into isolated output without changing tracked release assets.
- Hardware: real CLI default-10M measurement passed; actual MCP stdio profile switching, 4-byte and 4096-byte periodic measurements, and bit31 snapshot verification passed in all three profiles. Web REST switching while SuperWatch was sampling stopped the old stream and applied the chosen timing; saved medium profile survived disconnect/reconnect.
- Browser visual/click gate remains incomplete. The browser connection tool failed; Windows Computer Use then ended because it could not determine the browser URL confidently enough to enforce its policy. No further UI input was attempted. Component/API/HIL tests are not a substitute for this gate.
- No ordinary mem_read/mem_write or RTT performance results are claimed. No target write was performed. No ARM 20 MHz HIL, installer rebuild, release, or merge was performed.
