# STM32F103RET6 SWD clock calibration

Date: 2026-09-13. Replacement STM32F103RET6 board, RT-Thread 5.1.0,
72 MHz target CPU; LA5032 at 500 MSa/s, CH1 SWDIO / CH2 SWCLK.
This is a development qualification, not a firmware release.

## Findings and fixes

The old generic delay formula did not match the current ILM SWD loop.
For example, a 1 MHz request measured about 2.97 MHz and a 5 MHz request
about 9.35 MHz. The calibrated ARM path now derives its delay from measured
periods. JTAG retains its separate timing path. Actual GPIO SWD clocks are
phase dependent: read data, write data and headers do not have equal periods.

The host now applies a saved raw SWD clock even on deferred GUI connection,
applies changes made while connected under the exclusive probe control lease,
and requires the probe's exact acknowledgement before recording success.
Rejected changes do not replace the saved configuration.

True 20/30 MHz ARM experiments still failed on the replacement board. A
candidate that passed at nominal 20 MHz actually measured about 17.7 MHz;
it does not qualify 20 MHz. Production ARM clock requests above 10 MHz remain
rejected; HPM JTAG profiles are unaffected. Keil's current selector itself
offers a maximum of 10 MHz.

single RAM word, changing variable, 64-byte RAM, 4 KiB RAM, 4 KiB Flash,

runs 30 seconds. Payload comparison, frame CRC, firmware loss flags and
transfer error checks passed. Startup command bytes are excluded from stream

## RTT stop command correction

Repeated RTT sessions exposed an independent firmware bug: bytes of the
reserved `RTTView.stop()` command were forwarded to the target before the
whole command was recognized. The next shell command was consequently
prefixed with stale text. A bounded prefix filter now holds possible command
bytes, consumes complete matches, and preserves ordinary mismatches and
overlapping prefixes. Buffer metadata and signature read failures are checked
before forwarding ordinary input.

Updated UF2 SHA-256:
`ace4e914081741ea5055075ae560b543388aa43fcffb15bde620d0385edd1d2a`.
Native C filter boundary tests and the firmware build passed. On this version,
4/10 MHz sequential RTT `version` commands both returned RT-Thread 5.1.0.
Each speed also completed two 3-second SystemView captures (about 35,000–39,000
decoded events each), with no dropped packets/bytes and no new SWD errors.
These are short functional tests, not long-duration RTT/SystemView endurance.
An earlier isolated parity error remains recorded; its root cause has not been
proven and it is not silently removed from the qualification history.

## Host and browser validation

117 relevant Python tests passed, covering clock acknowledgements, deferred
connection, configuration changes, speed profiles and flash verification.
Chrome showed the saved 4 MHz setting on reconnection and the backend reported
4 MHz/low. The same GUI configuration API was then exercised on the real device, including
changing 4 to 10 MHz while SuperWatch was running. The control lease stopped
the stream, applied the clock and allowed a clean restart. LA read-data clocks
were 3.867/9.385 MHz, and SuperWatch reported zero read errors/drops at both
speeds. The default was restored to 10 MHz and acquisition stopped.

The full Chrome waveform screenshot gate remains pending: the minimum-period
alert interrupted browser automation. API verification is not substituted for
that outstanding GUI gate.

Raw captures and per-case JSON remain in the local target project's ignored
test output. Device identifiers, firmware binaries and LA capture files are
not included in this repository.
